# Глава 2. Проектирование информационной системы фитнес-центра

Задачей данной главы является разработка структурных и поведенческих моделей системы: определение ролей пользователей, проектирование схемы базы данных, описание ключевых бизнес-процессов и формирование требований к техническому и программному обеспечению.

---

## 2.1. Анализ требований и ролевая модель системы

Разрабатываемая информационная система ориентирована на автоматизацию четырёх ключевых процессов фитнес-центра: управления абонементами, записи на тренировки, ведения расписания тренеров и мониторинга прогресса клиентов. Дополнительно система предоставляет доступ к встроенному AI-консультанту.

В системе предусмотрено четыре роли пользователей:

| Роль | Описание |
|---|---|
| **Admin** | Полный доступ к системе: управление пользователями, просмотр журнала аудита |
| **Manager** | Оперативное управление: клиенты, тренеры, расписание, абонементы, финансы |
| **Trainer** | Управление собственными слотами, просмотр и редактирование прогресса клиентов |
| **User (Клиент)** | Бронирование тренировок, покупка абонементов, отслеживание прогресса, AI-консультант |

Неавторизованный посетитель может просматривать каталог абонементов, расписание групповых тренировок и список тренеров, однако для любых активных действий требуется регистрация.

## 2.2. Проектирование базы данных

### 2.2.1. Концептуальное проектирование

На концептуальном уровне выделены 13 сущностей. Центральной является **Users** — пользователь системы, который в зависимости от роли выступает клиентом, тренером или менеджером. Все остальные сущности связаны с ней напрямую или транзитивно.

Ключевые связи:

- **Users → Purchases** (1:N) — один клиент может забронировать или оплатить несколько абонементов.
- **Memberships → Purchases** (1:N) — тип абонемента может быть приобретён несколькими клиентами.
- **Users (Trainer) → PersonalWorkouts** (1:N) — тренер открывает временные слоты.
- **Users (Client) → PersonalWorkouts** (1:N, nullable) — клиент бронирует слот; при удалении клиента поле обнуляется.
- **Trainings → Bookings** (1:N) — групповая тренировка принимает несколько записей клиентов.
- **ProgressTrackers → ProgressEntries** (1:N, cascade) — трекер показателя хранит историю замеров.

## 2.3. Проектирование бизнес-процессов

### 2.3.1. Жизненный цикл персональной тренировки

Персональная тренировка в системе проходит строго определённую последовательность состояний, закреплённых перечислением `PersonalWorkoutStatus`. Переход между состояниями инициируется разными акторами: тренером, клиентом или менеджером.

**Описание переходов:**

1. Тренер создаёт временной слот → **Available** (ClientId = NULL).
2. Клиент бронирует слот (при наличии оплаченного абонемента) → **BookedUnpaid**. Оплата ещё не подтверждена.
3. Клиент или менеджер отменяет бронь → возврат в **Available**.
4. Менеджер подтверждает факт оплаты в разделе «Финансы» → **Paid**.
5. Альтернативный путь: менеджер назначает клиента напрямую, минуя шаг 2 → сразу **Paid**.
6. После истечения времени слота тренеру становятся активны кнопки результата:
   - «Тренировка проведена» → **Completed**.
   - «Не проведена» (с обязательным вводом причины) → **NotCompleted**.

### 2.3.2. Процесс бронирования и оплаты абонемента

Клиент выбирает тип абонемента из каталога и оформляет бронирование. Запись в таблице `Purchases` создаётся со статусом `Reserved` — цена зафиксирована, но доступ к тренировкам не открыт. Менеджер видит все забронированные (неоплаченные) абонементы на вкладке «Финансы → Абонементы» и подтверждает факт оплаты. После подтверждения статус меняется на `Paid`, и клиент получает доступ к бронированию тренировок.

Менеджер также может самостоятельно выдать абонемент клиенту через панель управления — в этом случае статус сразу устанавливается в `Paid`.

### 2.3.3. Процесс записи на групповую тренировку

Условием записи является наличие хотя бы одного абонемента со статусом `Paid`. Проверка выполняется сервисом `MembershipAccessService` перед созданием записи в `Bookings`. Дополнительно применяется частичный уникальный индекс по полям `(TrainingId, UserId)` для строк с `Status = Active`, что исключает двойную запись одного клиента на одно занятие, но сохраняет возможность повторной записи после отмены.

## 2.4. Проектирование структуры системы

Проектирование структуры системы выполнено на основе декомпозиции бизнес-процессов фитнес-центра. Система спроектирована как совокупность функциональных модулей, разграниченных по ролевому принципу: клиентская часть обеспечивает самостоятельную запись и контроль прогресса, административная панель — управление расписанием, клиентской базой и финансами, а тренерский кабинет — работу с собственным расписанием и данными подопечных.

Функциональная структура системы сформирована с учётом разделения полномочий между четырьмя категориями пользователей. Основными действующими лицами (акторами) являются: **Клиент**, **Тренер**, **Менеджер** и **Администратор**.

**Клиент** — основной пользователь системы, взаимодействующий с публичными и персональными разделами. К его функциям относятся:
- Самостоятельная регистрация и управление профилем: загрузка аватара, просмотр истории записей и абонементов.
- Работа с абонементами: просмотр каталога, бронирование выбранного тарифа; оплата подтверждается менеджером офлайн.
- Запись на тренировки: выбор групповых занятий из расписания или персонального слота у конкретного тренера при наличии оплаченного абонемента.
- Отслеживание прогресса: ведение трекеров антропометрических показателей с историей замеров.
- AI-консультант: чат с персональным AI-тренером (до 10 сообщений в сутки); доступен только при наличии активного абонемента.

**Тренер** — специалист, управляющий собственным расписанием и работающий с клиентами. Его функционал ограничен рамками профессиональной деятельности:
- Создание временных слотов для персональных тренировок с автоматическим расчётом цены по формуле: `Цена = 1000 + (Ранг − 1) × 500`.
- Просмотр своего расписания: кто записан, статус оплаты, контактный телефон клиента.
- Фиксация результата тренировки после её окончания: отметка «Проведена» или «Не проведена» с обязательным указанием причины.
- Просмотр и обновление антропометрических показателей клиентов, с которыми есть совместная запись.

**Менеджер** — сотрудник, осуществляющий оперативное управление фитнес-центром через административную панель:
- Управление клиентской базой: создание учётных записей, смена пароля, просмотр статуса абонемента.
- Назначение вручную: менеджер может самостоятельно записать клиента на групповую или персональную тренировку, а также выдать абонемент — в таком случае статус сразу устанавливается как «Оплачен».
- Финансовый учёт: подтверждение оплаты забронированных абонементов и персональных тренировок через вкладку «Финансы».
- Управление каталогами: редактирование профилей тренеров, создание и удаление абонементов, управление групповым расписанием.

**Администратор** — роль с расширенными системными правами:
- Управление учётными записями всех пользователей и назначение ролей.
- Просмотр журнала аудита: полная история операций создания, изменения и удаления данных с указанием автора и времени.

### 2.4.1. Диаграмма деятельности: жизненный цикл персональной тренировки

Диаграмма деятельности описывает логику ключевого бизнес-процесса системы — полный жизненный цикл слота персональной тренировки от создания тренером до фиксации результата. Модель построена по принципу TO-BE и отражает взаимодействие трёх акторов: Тренера, Клиента и Менеджера.

**Описание алгоритма процесса:**

*Этап создания слота.* Тренер открывает временной слот в личном кабинете. Система автоматически вычисляет стоимость на основе ранга тренера. Слот получает статус `Available`, поле `ClientId` остаётся пустым.

*Этап бронирования.* Возможны два сценария. В первом — клиент самостоятельно выбирает тренера и нажимает «Забронировать». Система проверяет наличие оплаченного абонемента: при его отсутствии действие недоступно. При успешной проверке за слотом закрепляется `ClientId`, статус меняется на `BookedUnpaid`. Клиент и тренер получают доступ к контактному телефону друг друга. Во втором сценарии менеджер назначает клиента напрямую через административную панель — статус сразу устанавливается в `Paid`, минуя промежуточный шаг.

*Этап подтверждения оплаты.* Если бронирование произведено клиентом, менеджер видит запись на вкладке «Финансы → Персональные тренировки» и после фактической оплаты подтверждает её. Статус меняется на `Paid`. Отмена бронирования клиентом или менеджером до подтверждения возвращает слот в состояние `Available`.

*Этап фиксации результата.* После истечения времени слота в кабинете тренера становятся активными кнопки «Тренировка проведена» и «Не проведена». При выборе второго варианта система требует ввода причины. Итоговый статус (`Completed` или `NotCompleted`) вместе с причиной отображается в панели менеджера.

### 2.4.2. Диаграмма классов

Для проектирования внутренней структуры системы построена диаграмма классов. Архитектура реализована с применением паттерна **BCE (Boundary–Control–Entity)**, что обеспечивает независимость слоёв и упрощает сопровождение системы.

**Слой Boundary (представление).** Содержит React-компоненты пользовательского интерфейса, каждый из которых инкапсулирует логику отображения и взаимодействие с пользователем. Публичные страницы: `RegisterPage`, `LoginPage`, `MembershipsPage`, `TrainingsPage`. Клиентский кабинет: `ProfilePage`, `PersonalWorkoutsPage`, `ProgressPage`. Тренерский кабинет: `TrainerSchedulePage`, `TrainerClientProgressPage`. Административная панель: `AdminClientsPage`, `AdminFinancesPage`, `AdminTrainingsPage`, `AdminPersonalWorkoutsPage`, `AdminCoachesPage`, `AdminMembershipsPage`.

**Слой Control (бизнес-логика).** Представлен сервисами ASP.NET Core, которые выступают посредниками между контроллерами API и базой данных. `AuthService` — регистрация, вход, выдача JWT-токена. `PurchaseService` — бронирование и подтверждение оплаты абонементов. `PersonalWorkoutService` — управление слотами и жизненным циклом персональных тренировок. `BookingService` — запись на групповые занятия с проверкой лимита мест и наличия активного абонемента. `MembershipAccessService` — проверка наличия оплаченного абонемента перед любым действием, требующим членства. `AiTrainerService` — формирование системного промпта, проверка суточного лимита обращений и маршрутизация запроса к API DeepSeek. Контроллеры (`AuthController`, `AdminController`, `TrainerController` и другие) принимают HTTP-запросы, проверяют JWT и делегируют обработку соответствующему сервису.

**Слой Entity (доменные модели).** Нижний уровень представлен классами-сущностями EF Core, непосредственно отображающими таблицы PostgreSQL: `User`, `Membership`, `MembershipOption`, `Purchase`, `Training`, `Booking`, `PersonalWorkout`, `ProgressTracker`, `ProgressEntry`, `AiTrainerUsage`, `AiTrainerMessage`, `AuditLog`. Перечисления `PurchaseStatus` (`Reserved`, `Paid`) и `PersonalWorkoutStatus` (`Available`, `BookedUnpaid`, `Paid`, `Completed`, `NotCompleted`) формализуют допустимые состояния ключевых объектов предметной области. Связи между классами отражают иерархию системы: компоненты Boundary инициируют HTTP-запросы к слою Control, который манипулирует объектами Entity через `AppDbContext` с провайдером Npgsql.

## 2.5. Требования к обеспечению системы

### 2.5.1. Требования к хранению и безопасности данных

- Данные хранятся в СУБД PostgreSQL 16 в кодировке UTF-8.
- Схема управляется через `AppDbContext.EnsureCreated()` и скрипты начального заполнения в `SeedData.cs`.
- Фотографии профилей и тренеров хранятся в локальной директории `wwwroot/uploads` и раздаются через механизм статических файлов ASP.NET Core.
- Конфигурационные секреты (строка подключения, JWT-ключ, API-ключ DeepSeek) вынесены в переменные окружения и не хранятся в коде.
- Все изменения данных фиксируются в таблице `AuditLogs` автоматически через EF Core Interceptor.

### 2.5.2. Требования к программному обеспечению

**Серверная часть:**
- Платформа: .NET 8, ASP.NET Core
- ORM: Entity Framework Core 8 с провайдером Npgsql
- Валидация: FluentValidation
- Хеширование паролей: BCrypt.Net
- AI-интеграция: OpenAI .NET SDK 2.1.0 с кастомным endpoint DeepSeek

**Клиентская часть:**
- Фреймворк: React 18, TypeScript
- UI-библиотека: Material UI 5
- Управление состоянием: Zustand
- HTTP-клиент: Axios
- Сборщик: Vite

**Инфраструктура:**
- Контейнеризация: Docker, Docker Compose
- СУБД: PostgreSQL 16
- Инструменты моделирования: PlantUML, Draw.io

### 2.5.3. Требования к техническому обеспечению

**Сервер:**
- Не менее 2 ядер CPU и 4 ГБ RAM для контейнерного развёртывания.
- Постоянный выход в интернет для обращений к API DeepSeek.
- ОС с поддержкой Docker (Linux, Windows Server, macOS).

**Клиент:**
- Современный веб-браузер: Chrome 90+, Firefox 88+, Edge 90+.
- Доступ к сети.

### 2.5.4. Требования по стандартизации

При разработке системы соблюдены требования следующих нормативных документов:

- ГОСТ 34.602-89. Техническое задание на создание автоматизированной системы.
- ГОСТ 19.201-78. Техническое задание. Требования к содержанию и оформлению.
