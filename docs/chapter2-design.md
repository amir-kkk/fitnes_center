# Глава 2. Проектирование структуры системы

Целью создания приложения являются следующее:

- Автоматизация процесса записи клиентов на групповые и персональные тренировки;
- Обеспечение прозрачного взаимодействия клиентов, тренеров и администраторов в единой системе;
- Организация продажи и управления абонементами онлайн;
- Предоставление клиентам инструментов отслеживания спортивного прогресса и персональных AI-рекомендаций.

Пользователями системы могут стать:

- Клиенты, приобретающие абонементы и записывающиеся на тренировки;
- Тренеры, управляющие своим расписанием и работающие с прогрессом клиентов;
- Администраторы, управляющие всем содержимым системы.

База данных в веб-приложении играет ключевую роль, обеспечивая хранение, организацию и доступ к данным, необходимым для функционирования приложения. Поэтому база данных фитнес-центра будет хранить в себе:

- Информация о пользователях: полное имя, электронная почта, роль в системе, фотография профиля;
- Данные об абонементах и фактах их приобретения клиентами;
- Расписание групповых и персональных тренировок с привязкой к тренерам;
- Записи клиентов на тренировки и история отмен;
- Антропометрические данные и замеры прогресса клиентов;
- Лог обращений к AI-консультанту для контроля дневного лимита.

Также функции в веб-приложении играют важную роль, обеспечивая организацию и управление различными аспектами приложения. Для предметной области фитнес-центра определены следующие функции:

- **Покупка абонемента:** Клиенты могут выбирать тип абонемента, оформлять покупку и подтверждать оплату онлайн. Наличие активного абонемента является обязательным условием для записи на тренировки.
- **Запись на тренировки:** Клиенты могут выбирать групповые занятия из общего расписания или выбирать конкретного тренера и бронировать персональный слот. Оплата персональной тренировки производится при физическом посещении.
- **Управление расписанием тренера:** Тренеры могут открывать доступные временные слоты в календаре. Цена персональной тренировки рассчитывается автоматически на основе ранга тренера по формуле: Цена = 1000 + (Ранг − 1) × 500.
- **Отслеживание прогресса:** Клиенты ведут трекеры антропометрических показателей. Тренер, имеющий забронированную персональную тренировку с клиентом, может просматривать и обновлять его показатели.
- **AI-консультант:** Клиентам с активным абонементом доступен чат с AI-тренером. Система формирует персональный системный промпт на основе данных пользователя из базы данных и ограничивает количество обращений до 10 в сутки.

Были определены следующие средства реализации:

- **Язык программирования (бэкенд):** C# с платформой .NET 8 и фреймворком ASP.NET Core.
- **Базы данных:** PostgreSQL (провайдер Npgsql для Entity Framework Core).
- **Frontend:** TypeScript с фреймворком React 18, библиотекой компонентов Material UI 5, сборщиком Vite.

## 2.1. Проектирование структуры базы данных

Проектирование структуры базы данных для фитнес-центра должно учитывать различные аспекты бизнеса: учёт пользователей и ролей, абонементы, расписание групповых и персональных тренировок, прогресс клиентов и историю взаимодействия с AI-консультантом.

**Таблица Users (Пользователи)**
- Id (уникальный идентификатор, UUID)
- Email (электронная почта)
- PasswordHash (хеш пароля, BCrypt)
- Role (роль: Admin, User, Trainer)
- FullName (полное имя)
- PhotoUrl (ссылка на фотографию профиля)
- TrainerRank (ранг тренера, 1–5, только для роли Trainer)
- CreatedAt (дата регистрации)

**Таблица Memberships (Абонементы)**
- Id (уникальный идентификатор)
- Name (название абонемента)
- Description (описание)
- Price (цена)
- DurationDays (срок действия в днях)
- CreatedAt (дата создания)

**Таблица MembershipOptions (Опции абонемента)**
- Id (уникальный идентификатор)
- MembershipId (идентификатор абонемента)
- OptionText (текст опции)

**Таблица Purchases (Покупки)**
- Id (уникальный идентификатор)
- UserId (идентификатор пользователя)
- MembershipId (идентификатор абонемента)
- PriceAtPurchase (цена на момент покупки)
- Status (статус: Pending, Paid)
- CreatedAt (дата покупки)

**Таблица Categories (Категории)**
- Id (уникальный идентификатор)
- Name (название категории)

**Таблица Trainings (Групповые тренировки)**
- Id (уникальный идентификатор)
- CategoryId (идентификатор категории)
- TrainerId (идентификатор тренера, ссылка на Users)
- Description (описание занятия)
- StartTime (дата и время начала)
- MaxParticipants (максимальное число участников)

**Таблица Bookings (Записи на групповые тренировки)**
- Id (уникальный идентификатор)
- TrainingId (идентификатор тренировки)
- UserId (идентификатор клиента)
- Status (статус: Active, Cancelled)

**Таблица PersonalWorkouts (Персональные тренировки)**
- Id (уникальный идентификатор)
- TrainerId (идентификатор тренера)
- ClientId (идентификатор клиента, может быть null для свободного слота)
- DateTime (дата и время)
- Price (цена, рассчитывается по рангу тренера)
- IsBooked (флаг занятости слота)

**Таблица ProgressTrackers (Трекеры прогресса)**
- Id (уникальный идентификатор)
- UserId (идентификатор пользователя)
- Title (название показателя: Вес, Грудь, Талия и т.д.)
- GoalValue (целевое значение)
- Unit (единица измерения)
- CreatedAt (дата создания)

**Таблица ProgressEntries (Замеры прогресса)**
- Id (уникальный идентификатор)
- TrackerId (идентификатор трекера)
- Value (значение замера)
- DateRecorded (дата замера)

**Таблица AiTrainerMessages (Сообщения AI-тренера)**
- Id (уникальный идентификатор)
- UserId (идентификатор пользователя)
- CreatedAt (дата и время отправки)

Каждая сущность с её свойствами является основой для определения структуры таблиц в базе данных. Необходимо учитывать, что таблицы должны быть связаны между собой. Поэтому в структуре таблиц необходимо предусмотреть наличие атрибутов, которые выполняют роль связывающих.

- **Пользователи и Покупки:** Каждый пользователь может совершить несколько покупок абонементов, но каждая покупка принадлежит только одному пользователю. Это классическая связь один-ко-многим между UserId в таблице Purchases и Id в таблице Users.
- **Абонементы и Покупки:** Один тип абонемента может быть куплен многократно разными пользователями. Связь один-ко-многим между MembershipId в таблице Purchases и Id в таблице Memberships.
- **Абонементы и Опции:** Каждый абонемент содержит несколько опций. Связь один-ко-многим между MembershipId в таблице MembershipOptions и Id в таблице Memberships; при удалении абонемента опции каскадно удаляются.
- **Категории и Тренировки:** Каждая групповая тренировка относится к одной категории, но категория может включать множество тренировок. Связь один-ко-многим между CategoryId в таблице Trainings и Id в таблице Categories.
- **Пользователи (Тренер) и Тренировки:** Каждая групповая тренировка ведётся одним тренером. Связь один-ко-многим между TrainerId в таблице Trainings и Id в таблице Users.
- **Тренировки и Записи:** На одну тренировку может быть несколько записей клиентов. Связь один-ко-многим между TrainingId в таблице Bookings и Id в таблице Trainings.
- **Пользователи и Записи:** Один пользователь может иметь несколько активных записей на тренировки. Связь один-ко-многим между UserId в таблице Bookings и Id в таблице Users.
- **Пользователи и Персональные тренировки (две связи):** Тренер открывает слоты (TrainerId → Users, каскадное удаление); клиент бронирует слот (ClientId → Users, установка NULL при удалении клиента). Уникальный индекс по паре (TrainerId, DateTime) исключает пересечение слотов одного тренера.
- **Пользователи и Трекеры прогресса:** Каждый трекер принадлежит конкретному пользователю. Связь один-ко-многим; при удалении трекера все его замеры каскадно удаляются.
- **Пользователи и AI-сообщения:** Каждое успешное обращение к AI фиксируется строкой с UserId и временем. Индекс по (UserId, CreatedAt) обеспечивает быстрый подсчёт суточного лимита.

Таким образом, каждая сущность и её атрибуты формируют основу для определения структуры таблиц базы данных, обеспечивая эффективное хранение и связь данных в системе.

### 2.1.1. Концептуальное проектирование структуры базы данных

Концептуальное проектирование структуры базы данных для фитнес-центра включает создание модели, которая точно отражает бизнес-процессы компании и обеспечивает надёжное и эффективное управление данными. Это важный этап, который определяет, как данные будут храниться, обрабатываться и взаимодействовать внутри информационной системы.

На концептуальном уровне выделены следующие ключевые сущности и их взаимосвязи:

- **Пользователь** является центральной сущностью системы. Он связан с покупками, записями на тренировки, трекерами прогресса и историей AI-обращений. В зависимости от роли пользователь выступает клиентом, тренером или администратором.
- **Абонемент** — продукт, реализуемый клиентам. Содержит список опций и связан с фактами продаж через сущность Покупка.
- **Тренировка (групповая)** принадлежит категории и проводится тренером. Связана с записями клиентов.
- **Персональная тренировка** соединяет тренера и клиента в конкретный временной слот. Цена определяется рангом тренера.
- **Прогресс** моделируется двумя связанными сущностями: трекер (тип показателя) и замер (конкретное значение в момент времени).

## 2.3. Требование к видам обеспечения

ИС «Фитнес-центр» создаётся как комплексная информационная система, которая должна являться организационно единым целым совокупностью частей. ИС «Фитнес-центр» должна представлять собой комплекс различных видов обеспечения.

### Требования к хранению данных

Все данные системы должны быть организованы в структурированном виде и управляться с помощью реляционной системы управления базами данных (СУБД). В качестве СУБД используется PostgreSQL версии 16.

Для хранения загружаемых файлов (фотографий пользователей и тренеров) используется локальная файловая система сервера в директории `wwwroot/uploads`. Файлы раздаются через встроенный механизм статических файлов ASP.NET Core.

### Требования к языкам программирования

- **Бэкенд:** разработка серверной части ведётся на языке C# с использованием платформы .NET 8 и фреймворка ASP.NET Core.
- **Фронтенд (статические страницы и компоненты):** используется TypeScript с фреймворком React 18.
- **Интерактивные компоненты клиентской части:** логика пользовательского интерфейса реализована на TypeScript; для сборки используется Vite.

### 2.3.1. Требования к информационной безопасности системы

Состав, структура и способы организации данных в системе определяются на этапе технического проектирования.

Уровень хранения данных должен быть построен на основе реляционной СУБД PostgreSQL. Для обеспечения целостности данных используются встроенные механизмы СУБД: первичные и внешние ключи, уникальные индексы, ограничения NOT NULL, каскадные удаления и установка NULL.

Аутентификация пользователей реализована на основе JWT (JSON Web Tokens). Токен содержит идентификатор пользователя, электронную почту и роль; передаётся в заголовке `Authorization: Bearer`. Пароли хранятся в хешированном виде с использованием алгоритма BCrypt.

Авторизация реализована через атрибуты `[Authorize]` и `[Authorize(Roles = "...")]` на контроллерах. Доступ к административным функциям ограничен ролью `Admin`; функции тренера — ролью `Trainer`; клиентские функции — ролью `User`.

Структура базы данных должна поддерживать кодирование хранимой информации в формате UTF-8.

Доступ к данным должен быть предоставлен только авторизованным пользователям с учётом их роли. Попытки несанкционированного доступа возвращают ответы с кодами HTTP 401 (не аутентифицирован) или HTTP 403 (недостаточно прав).

Система должна включать централизованный механизм обработки ошибок. Промежуточное программное обеспечение `ExceptionMiddleware` перехватывает необработанные исключения и возвращает стандартизированный JSON-ответ с соответствующим HTTP-кодом (400, 403, 404 или 500), не допуская утечки технических деталей в ответе.

### 2.3.2. Требования к эксплуатации системы

Система должна быть рассчитана на эксплуатацию в контейнеризованной среде на базе Docker. Приложение и база данных поставляются в виде сервисов в `docker-compose.yml`, что обеспечивает воспроизводимость среды и упрощает развёртывание.

Техническая защита данных обеспечивается конфигурированием переменных окружения (строка подключения, JWT-секрет, API-ключи) вне кода приложения — через `docker-compose.yml` или системные переменные среды.

Для нормальной эксплуатации приложение должно иметь постоянный доступ к СУБД PostgreSQL. При старте системы автоматически выполняются проверки схемы базы данных и заполнение начальными данными через `SeedData`.

В результате тестирования необходимо определить причины возникновения дефектов и принять меры для их устранения. Пользователи информационной системы должны получать понятные сообщения об ошибках через уведомления в пользовательском интерфейсе (компонент `NotificationSnackbar`).

ИС фитнес-центра должна обеспечивать правильную обработку аварийных ситуаций, которые возникают из-за неправильных действий пользователя, некорректного формата или недопустимых значений входных данных. Валидация входящих DTO выполняется через FluentValidation; ошибки возвращаются клиенту с HTTP-кодом 400 и описанием.

### 2.3.3. Требования по стандартизации

К требованиям стандартизации и унификации относятся:

- показатели, устанавливающие требуемую степень использования стандарта;
- типовые проектные решения;
- унифицированные методы реализации функций поставляемого программного обеспечения;
- классификаторы технико-экономической информации.

При разработке ИС формировании документации необходимо соблюдать требования следующих нормативных документов:

- ISO 12207:2008. Информационные технологии. Процессы жизненного цикла программного обеспечения;
- ГОСТ 34.602-89. Техническое задание на создание автоматизированной системы;
- ГОСТ 19.201-78. Техническое задание. Требования к содержанию и оформлению;
- ГОСТ 34.601-90. Комплекс стандартов на автоматизированные системы. Стадии создания;
- ГОСТ 34.201-89. Информационная технология. Виды, комплексность и обозначение документов при создании автоматизированных систем.

Моделирование должно выполняться с использованием нотации UML (диаграммы вариантов использования, деятельности, классов) и ERD (физическая и концептуальная модели данных), реализованных в инструментах PlantUML и Draw.io.

### 2.3.4. Требования к техническому, программному обеспечению системы и средствам реализации

Для создания эффективной информационной системы фитнес-центра важно чётко определить требования к техническому и программному обеспечению, а также к средствам реализации. Эти требования обеспечат поддержку всех необходимых бизнес-процессов и функциональных потребностей компании.

#### 2.3.4.1. Требования к техническому обеспечению

**Серверное оборудование:**
- Высокопроизводительные серверы для обработки и хранения данных.
- Достаточное количество процессоров и оперативной памяти (не менее 2 ядер CPU, 4 ГБ RAM для контейнерного развёртывания).
- Дисковое пространство для хранения базы данных и загружаемых медиафайлов (фотографий профилей и тренеров).
- Постоянное сетевое соединение для доступа к API DeepSeek (AI-консультант).

**Клиентское оборудование:**
- Персональные компьютеры или мобильные устройства с современным веб-браузером (Chrome 90+, Firefox 88+, Edge 90+).
- Доступ к интернету для работы с веб-приложением.

**Сетевая инфраструктура:**
- Сетевые коммутаторы и маршрутизаторы для обеспечения связи между серверами и клиентскими устройствами.
- Безопасная сеть с поддержкой HTTPS для шифрования передаваемых данных.

**Системное программное обеспечение:**
- Операционная система, поддерживающая Docker (Linux, Windows Server, macOS).
- СУБД PostgreSQL 16.
- Среда выполнения .NET 8 Runtime (в production-контейнере на базе `mcr.microsoft.com/dotnet/aspnet:8.0`).

#### 2.3.4.2. Требования к программному обеспечению

Для размещения данных системы и её программного обеспечения необходима среда выполнения .NET 8. Для управления СУБД рекомендуется использовать pgAdmin 4 или аналогичный инструмент. Прикладное программное обеспечение в составе системы должно соответствовать следующим основным требованиям:

- функционировать в среде операционной системы и взаимодействовать с пользователем в соответствии с требованиями настоящего ТЗ;
- поддерживать кириллицу (интерфейс полностью на русском языке);
- иметь удобный адаптивный пользовательский интерфейс, реализованный на базе Material UI;
- обеспечивать реализацию всех функций системы в соответствии с требованиями;
- возвращать понятные сообщения об ошибках для пользователей всех ролей.

Качество разработки программных средств обеспечивается автоматической валидацией входных данных (FluentValidation), централизованной обработкой исключений (ExceptionMiddleware) и типизацией на стороне фронтенда (TypeScript).

#### 2.3.4.3. Требования к средствам реализации

**Безопасность:**
- JWT-аутентификация с ограниченным временем жизни токена.
- Хранение паролей исключительно в хешированном виде (BCrypt).
- Ролевая авторизация на уровне контроллеров API.

**Резервное копирование и восстановление:**
- Системы для регулярного резервного копирования данных PostgreSQL (pg_dump).
- Хранение конфигурационных секретов (API-ключи, строки подключения) отдельно от кода — в переменных среды.

**Интеграция с внешними системами:**
- REST API (JSON) для взаимодействия фронтенда с бэкендом.
- Интеграция с DeepSeek AI через OpenAI-совместимый API (SDK OpenAI .NET 2.1.0 с кастомным Endpoint).
- Генерация ссылок для добавления занятий в Google Calendar (URL-шаблон TEMPLATE).

**Поддержка и обслуживание:**
- Возможность масштабирования через Docker Compose.
- Swagger UI (`/swagger`) для тестирования и документирования API в процессе разработки.
